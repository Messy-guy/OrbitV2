# Orbit Terminal Runtime V2 (Historical Plan)

> Superseded by [`plan.md`](./plan.md) as of 2026-09-13. The implemented
> architecture now uses Rust `alacritty_terminal` plus the native Canvas grid
> renderer; it does not use xterm.js as the authoritative emulator. Keep this
> file as historical context only and do not use its xterm-first migration
> instructions for new work.

Status: implemented V2 local-rendering transport; packaged-release validation pending
Last updated: 2026-09-11

## Decision

Stop adding provider-specific patches to the current terminal path. Rebuild the terminal subsystem as an isolated session transport with explicit attach/replay/live semantics, raw byte delivery, and a real terminal capability bridge.

The existing remote-control input path remains a compatibility boundary throughout the migration. The new runtime must be able to serve both the local xterm view and remote control through the same session handle.

## Implementation status

Implemented in the current worktree:

- session-scoped raw PTY byte broker with monotonic sequences, bounded replay,
  attach-before-spawn ordering, live delivery, exit frames, and stale-history
  resync errors;
- Tauri Channel IPC commands for attach/detach;
- `AgentTerminal` switched from global `agent-output` rendering to the V2
  transport, with duplicate suppression and replay reattach on sequence gaps;
- xterm capability hooks for DSR, DA, and known OSC color queries;
- legacy Rust capability replies retained only for headless sessions without a
  local xterm subscriber;
- provider launch failure no longer silently falls back to Bash for known AI
  CLIs, so packaged PATH failures surface as actionable errors;
- the existing `send_agent_input` command and remote-control services remain
  unchanged.

The remaining release gate is a packaged Linux smoke matrix on the target
device. The current Rust `PtyManager` remains the process/lifecycle owner
during this compatibility migration; replacing that internal owner is not
required to validate the production blank-render bug and would increase risk
to remote control without improving the attach contract.

## Architecture audit verdict

The plan is directionally industry-standard, with one important refinement: a terminal is three cooperating layers:

1. PTY/process I/O and process lifecycle.
2. A terminal emulator/parser that owns cursor, modes, screen cells, scrollback, and capability responses.
3. A renderer/input surface.

Modern terminal projects follow this separation. Ghostty describes dedicated read, write, and render threads per terminal and separates VT parsing/state from host integration. WezTerm reads the PTY on a dedicated thread, parses the stream, and applies actions to a terminal/multiplexer model. Windows ConPTY exposes a VT input/output stream between a pseudoconsole and a terminal renderer.

For Orbit, the first reconstruction should use xterm.js as the authoritative emulator for each attached local terminal, with a Rust session broker underneath it. A Rust-side emulator such as `libghostty-vt` or `alacritty_terminal` is a later option if Orbit needs authoritative offscreen rendering, multiple simultaneous clients, or server-side snapshots. Do not implement two independent terminal emulators in V2 without a concrete synchronization contract.

The plan is approved with these corrections:

- Raw PTY bytes remain unmodified in transport.
- xterm.js owns local terminal parsing and rendering in the first V2 implementation.
- xterm.js parser hooks may generate capability replies because xterm.js owns cursor and dimension state; this is a compatibility bridge, not a full terminal emulator replacement.
- Sequence-numbered replay is required for attach races, but raw replay is not a semantic screen snapshot. A future server-side emulator is required for efficient state snapshots after arbitrary sequence gaps.
- Tauri Channels are preferred for high-throughput IPC, but the implementation must verify binary payload behavior in the installed Tauri version instead of assuming `Uint8Array` serialization.

This is materially different from the current runtime because ownership and synchronization are explicit, not because it swaps one terminal widget for another.

## Why the current direction is being retired

The current path has several coupled responsibilities inside `PtyManager` and `AgentTerminal`:

- PTY spawning, provider resolution, startup delays, role prompt injection, terminal capability emulation, output history, Tauri event broadcasting, and process watching are mixed together.
- Frontend listeners identify output by comparing several possible agent/session IDs.
- Startup scrollback replay is heuristic and can be disabled by a control-only first output event.
- Rust converts PTY bytes to lossy UTF-8 strings before transport.
- Terminal capability responses are guessed in a Rust byte scanner rather than being generated by the terminal emulator that owns the cursor, mode, dimensions, and palette state.
- A broadcast event stream has no explicit attach point, sequence number, or replay boundary.

The observed production evidence is especially important: affected CLIs spawn, Rust reads output, and Rust emits output events, yet the packaged xterm remains blank. This requires a transport/attach contract, not another startup-delay heuristic.

## Target architecture

```text
                 ┌──────────────────────────────┐
                 │ ProviderLauncher             │
                 │ command + args + env policy  │
                 └──────────────┬───────────────┘
                                │ spawn
                        ┌───────▼────────┐
                        │ PtySession     │
                        │ child + master │
                        │ single writer   │
                        └───────┬────────┘
                                │ raw PTY bytes
                    ┌───────────▼───────────┐
                    │ SessionRegistry       │
                    │ session_id keyed      │
                    │ sequence + ring buf   │
                    └──────┬─────────┬──────┘
                           │         │
             local attach │         │ remote input adapter
                           │         │
                  ┌────────▼───┐ ┌───▼────────────┐
                  │ Tauri      │ │ RemoteControl  │
                  │ Channel    │ │ SessionHandle  │
                  └─────┬──────┘ └────────────────┘
                        │ raw bytes
                ┌───────▼────────┐
                │ TerminalView   │
                │ xterm.js       │
                │ parser hooks   │
                │ resize/input   │
                └────────────────┘
```

This preserves the industry-standard model: a native PTY owns the process terminal, the terminal emulator owns parsing/rendering/cursor state, and the application transports bytes and input between them.

## Backend V2 design

### 1. `TerminalSession` as the only runtime abstraction

Create a new Rust module under `src-tauri/src/terminal_v2/` rather than extending the current monolith:

```text
terminal_v2/
  mod.rs
  session.rs       // lifecycle and public SessionHandle
  registry.rs      // session_id -> Arc<TerminalSession>
  pty.rs           // portable-pty allocation and child process
  launcher.rs      // provider command resolution and launch errors
  stream.rs        // sequence-numbered output frames and replay ring
  lifecycle.rs     // spawn/attach/ready/exit/failure transitions
```

Each `TerminalSession` owns:

- `session_id`, `agent_id`, provider, workspace, and PID;
- PTY master, child, and one serialized input writer;
- a bounded output ring buffer, e.g. 256 KiB or configurable by settings;
- monotonically increasing output sequence numbers;
- lifecycle state and exit reason;
- attached stream count and last activity timestamps.

No component outside the session owns the PTY writer.

### 2. Explicit attach/replay/live protocol

Replace implicit global `agent-output` subscription with an attach handshake:

```text
create_or_reattach(session_id)
  -> session metadata
attach_output(session_id, from_sequence)
  -> Attached { current_sequence, rows, cols }
  -> Replay { sequence, bytes }*
  -> Live { sequence, bytes }*
```

The attach operation must establish the stream before a new process is allowed to emit user-visible output. Reattachment uses the last acknowledged sequence, not a boolean such as `receivedLiveOutput`.

The stream must define behavior for:

- attach before spawn;
- attach after spawn;
- attach after process exit;
- missed events;
- duplicate attach;
- slow renderer;
- history ring overflow.

### 3. Raw byte transport

Do not convert PTY chunks to `String::from_utf8_lossy` in the transport layer. Send raw bytes through a Tauri 2 `Channel` or an equivalent binary-capable stream. Keep metadata separate from bytes:

```ts
type TerminalFrame = {
  sessionId: string;
  sequence: number;
  kind: 'replay' | 'live' | 'exit' | 'error';
  bytes: Uint8Array;
};
```

If the chosen Tauri channel serialization cannot carry `Uint8Array` directly in the current version, use an explicit binary-safe envelope behind one adapter and test round-trip bytes. Do not use lossy text conversion. The transport should not become an event-sourced terminal emulator; its job is ordered delivery and bounded replay.

### 4. Terminal capabilities belong to the emulator side

Remove the ad hoc Rust `TerminalQueryResponder` from the authoritative V2 path. In the first V2 implementation, xterm.js is the local emulator and exposes parser hooks for CSI, OSC, DCS, APC, and ESC sequences. Register a capability bridge that can answer based on the actual xterm state:

- DSR cursor position from xterm’s active buffer cursor;
- terminal dimensions from the current xterm instance;
- supported device attributes and keyboard protocol;
- color queries from the active theme where appropriate.

The capability bridge writes responses through the same `SessionHandle.writeInput()` method as keyboard input. It must be tested independently and rate-limited. Unknown queries must be ignored, not guessed.

This keeps terminal semantics where the cursor and screen state actually exist. xterm.js parser hooks are documented at https://xtermjs.org/docs/guides/hooks/.

Do not add a second Rust VT parser in this phase. If Orbit later requires a canonical server-side terminal model, introduce it as a separately tested `TerminalEmulator` interface and define whether xterm receives raw bytes, semantic cell snapshots, or both.

### 5. Provider launcher with no silent shell fallback

Provider launch resolution becomes a typed result:

```rust
struct LaunchSpec {
    executable: PathBuf,
    args: Vec<OsString>,
    env: Vec<(OsString, OsString)>,
    cwd: PathBuf,
    terminal: TerminalEnvironment,
}
```

If a configured provider executable is not found, return a visible `LaunchError` containing provider, searched names, and searched directories. Do not silently start Bash and make the UI look like the provider failed.

The launcher owns only:

- executable aliases;
- augmented PATH;
- cwd;
- safe terminal environment (`TERM`, `COLORTERM`, geometry);
- provider-specific arguments that are verified by tests.

Startup sleeps and prompt injection are not part of the generic session transport. They become explicit provider launch policies and are disabled unless required by a provider contract.

### 6. PTY correctness

The PTY layer must:

- allocate the native PTY with the requested size before spawn;
- set the child as the controlling terminal through `portable-pty`;
- resize on every renderer size change;
- keep stdout/stderr combined through the PTY as a real terminal does;
- serialize writes from local input, capability replies, and remote control;
- report normal Linux PTY `EIO` close as exit, not as a rendering error;
- preserve process group interrupt/terminate behavior.

`portable-pty` remains a reasonable cross-platform PTY primitive; the redesign is around ownership and transport contracts, not a blind replacement of the PTY library.

## Frontend V2 design

Create a new `TerminalSessionView` and leave the old component available behind a feature flag during migration:

```text
src/services/terminalV2/
  terminalTransport.ts
  terminalCapabilities.ts
  terminalSession.ts
  terminalTypes.ts
src/components/agent/TerminalSessionView.tsx
```

The new view owns exactly one session:

1. Create/open xterm.
2. Fit and send initial dimensions.
3. Attach the binary output channel using `sessionId`.
4. Receive replay frames in sequence.
5. Switch to live frames after the attach barrier.
6. Register capability parser hooks.
7. Forward keyboard bytes through the session input adapter.
8. Acknowledge the last rendered sequence.
9. Detach without killing the session when the panel unmounts.

There should be no `agentId === ... || sessionId === ...` matching inside the terminal view. The view receives a concrete `sessionId` and channel.

The local terminal and remote control must use:

```ts
sessionHandle.write(bytes)
sessionHandle.resize(rows, cols)
sessionHandle.interrupt()
```

Remote control should not subscribe to the renderer’s React state or xterm DOM.

## Remote-control compatibility strategy

Do not modify these files during the first implementation:

- `src/services/remoteControl/UniversalRemoteController.ts`
- `src/services/remoteControl/ptyDelivery.ts`
- `src/services/remoteControl/ptySpawnTracker.ts`

Add an adapter behind the existing `tauriService.sendAgentInput` command so its external behavior remains identical. Internally, it resolves the same `TerminalSession` and calls the serialized writer.

Before removing the old runtime, run remote-control parity tests for:

- plain text input;
- control characters and Ctrl-C;
- multiline input;
- input during startup;
- input after reattach;
- concurrent local and remote writes;
- session replacement after a stale process exits.

## Migration sequence

### Phase 0: Freeze and measure

- Do not add more provider-specific terminal hacks to the old path.
- Keep `v0.1.39` as the known baseline.
- Add a diagnostic mode that records session/sequence counts without terminal contents.

### Phase 1: Build V2 beside V1

- Implement `TerminalSession`, registry, sequence ring, and attach protocol.
- Add a test-only echo PTY provider.
- Keep current `PtyManager` and remote commands unchanged.

### Phase 2: Local renderer canary

- Implement `TerminalSessionView`.
- Route only the built-in shell and Codex through V2.
- Verify text, ANSI, Unicode, alternate screen, cursor movement, resize, input, Ctrl-C, reconnect, and scrollback.

### Phase 3: Provider launch adapters

- Add OpenCode, Antigravity, KiloCode, Freebuff, Cline, Copilot, and other providers one at a time.
- Require explicit executable resolution logs and no shell fallback.
- Compare each provider in Orbit V2 against a normal terminal session.

### Phase 4: Remote-control parity

- Point the existing remote-control command adapter at V2 session handles.
- Run the complete remote-control matrix before changing any remote-control code.

### Phase 5: Default and removal

- Make V2 the default after a full provider matrix passes in packaged Linux builds.
- Keep V1 behind a temporary rollback flag for one release.
- Remove V1 only after a successful release and confirmed device testing.

## Required tests

### Rust integration tests

- PTY echo preserves exact bytes, including invalid UTF-8 byte sequences.
- Output sequence numbers are monotonic.
- Replay returns exactly the requested range.
- Ring overflow returns a clear resync error.
- Attach before spawn receives all output.
- Reattach receives history and then live output without duplication.
- Resize reaches the PTY.
- Normal `EIO` close becomes `Exited`.
- Real read errors become `Failed`.
- Concurrent writes are serialized.

### Frontend tests

- Frames are rendered in sequence order.
- Duplicate frames are ignored.
- Gap frames request replay/resync.
- Detach disposes listeners but does not kill the session.
- xterm parser capability replies use current cursor and dimensions.
- Terminal input is delivered exactly once.

### Packaged Linux smoke matrix

For each provider, test:

1. Fresh launch from desktop menu.
2. Launch from a project workspace.
3. First visible prompt/banner.
4. Keyboard input.
5. Resize.
6. Ctrl-C/exit.
7. Close/reopen panel and reattach.
8. Remote-control input.

## Explicit non-goals

- Do not wrap every CLI in `script` as a permanent architecture.
- Do not parse, strip, or normalize ANSI in the transport.
- Do not use a WebSocket or localhost server for local PTY transport unless Tauri IPC is proven insufficient.
- Do not invent provider-specific delays as the primary synchronization mechanism.
- Do not make remote control depend on the renderer or browser DOM.
- Do not claim success from a Rust unit test alone; packaged Linux smoke testing is required.
